# Supabase: отчёт по этапу 1

Дата: 8 ноября 2026 года. Выполнены только база данных, авторизация и подключение клиента. Удалённый Supabase-проект не изменялся.

## Что сделано

- Добавлены воспроизводимые миграции [`supabase/migrations/20261108000100_initial_schema.sql`](supabase/migrations/20261108000100_initial_schema.sql) и [`supabase/migrations/20261108000200_record_answer.sql`](supabase/migrations/20261108000200_record_answer.sql).
- Созданы семь согласованных пользовательских таблиц: `profiles`, `topics`, `cards`, `card_progress`, `training_sessions`, `answer_history`, `user_achievements`. У всех включён RLS. Связи карточек, прогресса, сессий и ответов проверяют совпадение `user_id` у связанных записей. Темы и карточки имеют `deleted_at`; прямое физическое удаление через браузерные роли запрещено.
- Для `anon` отозваны права на пользовательские таблицы. У `authenticated` есть чтение только собственных строк. Изменение `profiles`, `topics` и `cards` ограничено владельцем. Прогресс, сессии, ответы и достижения доступны браузеру только для чтения до реализации соответствующих серверных операций.
- Добавлена `record_answer`: функция с `SECURITY DEFINER`, пустым `search_path`, проверкой `auth.uid()`, владельца карточки и активной сессии, ограниченным `EXECUTE` и идемпотентностью по UUID события. На этом этапе она записывает **только историю ответа**; XP, интервалы и достижения не изменяет. Фронтенд её пока не вызывает.
- Перед удалённым применением добавлены проверки активной темы/карточки при создании карточек, активных сессий, прогресса и ответов. `record_answer` также отвергает карточку под мягко удалённой темой. Проверки используют блокировки строк, чтобы создание не обгоняло мягкое удаление.
- `deleted_at` нельзя менять прямым клиентским `UPDATE`. Для владельца предусмотрены отдельные RPC `soft_delete_topic`, `restore_topic`, `soft_delete_card`, `restore_card` с `SECURITY DEFINER`, пустым `search_path` и ограниченным `EXECUTE`. Восстановление карточки требует активной темы. Восстановленная тема вновь открывает свои карточки, которые не были удалены отдельно; отдельно удалённые карточки восстанавливаются явно.
- `record_answer` повторно проверяет UUID события после ожидания блокировки сессии и определяет успешную вставку через `INSERT … ON CONFLICT DO NOTHING RETURNING id INTO`. Повтор с тем же UUID и другими данными отклоняется. Повтор того же ответа допустим даже после завершения сессии.
- Созданы единый клиент Supabase, слой входа/выхода и начальный слой чтения тем и карточек в [`src/lib/supabase/`](src/lib/supabase/). Клиент использует только `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` из окружения. Значения переменных в отчёт не включены.
- Добавлен экран входа по email и паролю в существующем стиле. Внутренние экраны закрыты до восстановления сессии; сессия сохраняется SDK после перезагрузки. Кнопка выхода доступна и на обычных экранах, и в тренировке. Формы регистрации нет.
- Добавлены [`.env.example`](.env.example), [`supabase/config.toml`](supabase/config.toml) с отключённой локальной регистрацией и pgTAP-набор [`supabase/tests/database/owner_rls_test.sql`](supabase/tests/database/owner_rls_test.sql).

Демоданные, Dashboard, логика тренировки и визуальный стиль существующих экранов сохранены. После входа приложение пока показывает демонстрационный прототип; чтение облачных тем и карточек подготовлено, но не подключено к экранам до этапа 2.

## Как применить миграции к своему проекту

Все команды выполняются из корня проекта. Supabase CLI добавлен в `devDependencies`; используйте `npx supabase`.

1. В Supabase Dashboard убедитесь, что проект выбран верно. Если в `public` уже существуют таблицы с такими именами, сначала сравните их со схемой и сделайте резервную копию: эта миграция рассчитана на проект без этих семи таблиц.
2. Авторизуйте CLI и привяжите именно ваш проект:

   ```sh
   npx supabase login
   npx supabase link --project-ref <PROJECT_REF>
   ```

3. Проверьте список изменений без применения:

   ```sh
   npx supabase db push --dry-run --remote
   ```

4. После проверки примените миграции **вручную**:

   ```sh
   npx supabase db push --remote
   ```

Команду `db reset --remote` не используйте: она пересоздаёт удалённую базу. См. [официальный порядок работы с миграциями](https://supabase.com/docs/guides/local-development/cli-workflows).

## Как создать владельца

1. В Supabase Dashboard откройте Authentication и убедитесь, что вход по email и паролю включён.
2. В настройках Auth выключите **Allow new users to sign up** и **Allow anonymous sign-ins**. Локальный `config.toml` уже запрещает регистрацию, но он сам по себе не меняет настройки удалённого проекта. [Настройки Supabase Auth](https://supabase.com/docs/guides/auth/general-configuration).
3. Откройте **Authentication → Users → Add user**. Если доступно создание пользователя с паролем, создайте владельца и подтвердите email. Иначе отправьте приглашение через **Send invitation**, завершите подтверждение email и задание пароля по ссылке. [Пользователи и приглашения Supabase](https://supabase.com/docs/guides/auth/users).
4. Для приглашения проверьте `Site URL` и разрешённые Redirect URLs в Auth: они должны включать адрес приложения, на котором вы будете открывать ссылку.

Пароль вводится только в форму Supabase Auth; приложение не хранит его самостоятельно.

## Как проверить вход и RLS

1. Запустите `npm run dev`. Без сессии любой внутренний URL, например `/#dashboard` или `/#training`, должен показать только экран входа.
2. Войдите учётной записью владельца. После обновления вкладки сессия должна восстановиться, а кнопка выхода вернуть на экран входа.
3. Для локальной проверки политик установите и запустите Docker, затем выполните:

   ```sh
   npx supabase start -x realtime,storage-api,imgproxy,postgres-meta,studio,edge-runtime,logflare,vector,supavisor
   npx supabase test db
   ```

   Тест внутри транзакции создаёт двух временных пользователей и проверяет доступ владельца, отказ другому пользователю, отсутствие прав у `anon`, составную защиту данных и идемпотентность RPC. Данные теста откатываются.

4. В удалённом проекте не создавайте второго пользователя ради проверки без необходимости. Если он уже есть, убедитесь через отдельную авторизованную сессию, что он не видит темы, карточки и историю владельца. RLS-тесты локальной базы дают такую проверку без изменения данных удалённого проекта.

## Граница этапа

CRUD тем и карточек, алгоритм повторения, начисление XP, достижения, массовый импорт и замена демопоказателей не реализованы. Это следующий этап после отдельного подтверждения.

Для следующего этапа нужны серверные операции создания и завершения `training_sessions`: они должны проверять владельца и активную тему, атомарно менять статус и однократно выдавать бонус за завершение. Прямые права браузерной роли на запись в `training_sessions`, `card_progress`, `answer_history` и `user_achievements` выдавать нельзя.

Перед начислением XP нужен второй ключ идемпотентности для **логической попытки ответа**. UUID события защищает от повторной отправки того же запроса, но два разных UUID могут описывать один и тот же показ карточки. В будущем сервер должен выдавать или регистрировать `attempt_id` при показе карточки и обеспечить уникальность `(user_id, session_id, attempt_id)` в истории. Уникальность только `(session_id, card_id)` не подходит: свободная тренировка допускает повторное появление карточки в одной сессии. Правила XP и повторения в текущих миграциях не добавлялись.
